# ELM327 over BLE: generic OBD-II scanners as a live source

Status: implemented, unverified on hardware. Test adapter: Vgate vLinker MC+ (BLE). Out of scope by decision: Bluetooth
classic (SPP) adapters and workarounds for counterfeit ELM327 v1.5 clones.

## Problem

An ELM327 adapter stores nothing: it answers one command at a time while something is connected.
Rows exist only while the phone holds the link and polls, so this source is a stream
(`Source.subscribe()`, plan "Source classes"), collected by the drive session of ticket 0001.

## Shape

**Core, `core/.../core/elm327/`** (pure Kotlin, JVM-tested against a scripted fake adapter):

- `VehicleProfiles`: wican-fw's `vehicle_profiles.json` from the core resource (82 profiles,
  unchanged, see the resource README). `VehicleProfile(carModel, init, pids)`,
  `Pid(command, init, parameters)`, `Parameter(name, expression, unit, deviceClass, min, max)`;
  `init` strings split on `;`. `VehicleProfiles.GENERIC` is the file's "AAA: Generic" mode-01
  profile, for cars without one.
- `ByteExpression.evaluate(expression, bytes)`: wican-fw `expression_parser.c` grammar.
  Decimal numbers, `B<n>` (unsigned byte n of the response), and the forms the profiles use
  beyond that: `S<n>` (signed byte), `B<n>:<bit>`, `[B<a>:B<b>]` / `[S<a>:S<b>]` (big-endian
  ranges); `+ - * /`, `& | ^`, `<< >>`, parentheses; precedence `| ^` < `&` < shifts < `+ -` <
  `* /`; bitwise and shifts on int-truncated operands; no unary operators. A `B<n>` past the end
  of the response, division by zero or a value outside the parameter's min/max (dropped, as
  wican-fw does) is an error for that parameter only.
- Response bytes follow wican-fw `autopid.c`: the adapter runs `ATE0 ATL0 ATS1 ATH1 ATST96`;
  each answer line is `<header> <bytes…>` (header 3 hex digits for 11-bit; 29-bit as
  `18 DA F1 10`, which is what `ATS1` prints, or 8 digits); the
  bytes of every line after its header are concatenated in line order, PCI bytes included, and
  `B0` is the first of them. Status lines (`NO DATA`, `ERROR`, `?`, `STOPPED`, `UNABLE TO
  CONNECT`, `BUS INIT…`, `CAN ERROR`, `BUFFER FULL`) mean the PID yields nothing this round;
  `SEARCHING...` is skipped.
- `Elm327Transport(link: GattLink, scope)`: `command(cmd)` writes `cmd\r` and returns the text
  up to the `>` prompt (echo and prompt stripped); no prompt within 5 s is an `IOException`.
  Profile `init`/`pid_init` commands that would undo the format (`ATE1`, `ATH0`, `ATS0`) are
  skipped, as wican-fw does.
- `Elm327Source(transport, profile, pollInterval = 2 s, clock)`: `subscribe()` resets (`ATZ`),
  configures, runs the profile `init`, then polls every `pollInterval`: per PID its `pid_init`
  when it differs from the previous PID's, the command, decode, one row per parameter
  `{"ts":<phone ms>,"param":"autopid.<NAME>","value":<number>}`, plus `elm327.voltage` from
  `ATRV` each round and `elm327.adapter` `{"version":…}` once per connection, with the first
  round that decoded something. A round that decoded nothing emits an empty list, voltage
  included (the session's idle rule counts it). `pull` answers an
  empty page, `clockJournal` is empty, `deviceStatus` null: rows are phone-stamped and rate
  `device`.

**App** (implemented, tasks L10 and L12: kind, layout discovery, pair wizard and probe, and the drive
session streams it; nothing verified on hardware, see `planning/testplans/elm327.md`):

- `DeviceKind.ELM327`, `Elm327Support`: source prefix `elm327:`, live mode stream, never a
  periodic or presence sync target. CDM filter by name (`vLinker`, `V-LINK`, `OBD`, `ELM`,
  case-insensitive) or one of the known services.
- GATT layout is discovered once at pairing and stored in `DeviceConfig`: the first known pair
  present (`FFF0`: `FFF1` notify / `FFF2` write; `FFE0`: `FFE1` both; `18F0`: `2AF0` / `2AF1`;
  Nordic UART `6E400001`: `6E400003` / `6E400002`; WiCAN `FEE0`: `FEE3` / `FEE1`), else the
  first service with a notify and a write characteristic. Sessions open the stored layout; a
  device without one (test step skipped) is searched on its first link and the pick stored then.
- Pair wizard: kind "OBD-II scanner (ELM327)", vehicle profile picker (searchable car models plus
  Generic), probe shows adapter version (`ATZ`) and battery voltage (`ATRV`).
- Drive session (ticket 0001) collects `subscribe()`: each emission is stored as a page with
  cursor `session:<start ms>:<n>` under a `{"_file":"elm327/<start ms>"}` marker, normalised
  with an empty journal, so sealing, dedupe and uploads are unchanged.

## Acceptance

- Against the scripted fake: the EV6 profile's `220101` multi-frame answer decodes `SOC`
  and the four cumulative counters, whose byte indexes skip the consecutive frames' PCI bytes.
- On the vLinker MC+ with the car on: a session stores rows every poll, the status screen shows
  the row count, and a sink receives `autopid.*` rows with the same names a WiCAN would write.
- Car off: every PID answers a status line, rounds emit nothing, the session ends by the idle rule.

## Known gaps

Multi-ECU answers (several headers to one request) are concatenated in line order; wican-fw
prefers the lowest header when more than two frames differ. 29-bit headers untested. Adapter
sleep behaviour (some sleep after minutes idle on the port) is the adapter's.
